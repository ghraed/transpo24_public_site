# Transpo24 privacy implementation review

Reviewed 9 September 2026. Scope: public website, Customer App, Driver App, and a read-only review of backend providers/account deletion. This records source-level findings and implementation evidence; it is not a legal certification or a production traffic audit.

## Implemented

- No optional analytics or advertising integration was found in the three frontends' direct dependencies or application source. Firebase configuration is used for push delivery; no Firebase Analytics integration was found. No consent modal or ATT prompt was added for an absent tracking purpose.
- Website: replaced the dead Cookies link with `/cookies`, added route metadata and sitemap entry, and kept legal navigation usable on small screens. The additional blanket CSP restriction was removed following the requirement to preserve feature integrations. Existing website resource-loading behavior is unchanged.
- Both apps: privacy screens now show a short explanation, a user-initiated device-settings button, and a privacy-request email link with a readable fallback. The new copy is supplied in English, French, German, Arabic, Spanish and Italian. Registration still requires the existing terms checkbox; wording no longer presents the privacy notice as consent to optional processing. Booking, payment, OTP and trip-state rules are unchanged. Driver background location supplements the existing foreground watchers; account sign-out additionally stops its location task.
- The background-location block was removed from both apps. Driver background location and its Android foreground service are enabled; the pre-existing driver FOREGROUND_SERVICE exclusion was removed because it prevents this feature. Advertising-ID/microphone exclusions do not affect existing transport features. The Driver location message explains foreground/background live position sharing during pickup/delivery. These native changes need new app binaries; an OTA JavaScript update alone does not apply them.
- Synchronized privacy notices across the three repositories, covering permissions, local storage, current feature providers, legal grounds, retention criteria, transfer enquiries, requests and supervisory authorities. Existing company details were preserved pending confirmation. No unverified hosting country, representative or exact retention duration was invented.
- `npm run privacy:check` checks the direct runtime-dependency baseline, selected tracking signatures and native privacy configuration. It runs before the website build and app type checks. Review new dependencies before updating `privacy-baseline.json`. This is a regression aid, not a universal tracker detector; it does not audit transitive SDK behavior, remotely configured features or infrastructure.

## If optional tracking is added later

Review the purpose/provider first. Keep the SDK and its storage/network processing off before a valid choice. Offer purpose-specific accept/refuse choices with equal ease, explain providers and retention, version and retain appropriate consent evidence, and offer withdrawal from a persistent privacy entry point. Refusal, missing/corrupt/expired choices and withdrawal must leave unrelated transport features usable. Handle provider shutdown and deletion of optional identifiers when withdrawing. Add ATT only when the actual integration meets Apple's tracking definition; ATT is additional to other required consent. Validate every state with runtime/network tests before release.

## Active-trip background location correction

The original driver app used foreground watchers only. The new SDK 56 TaskManager task sends current positions while minimized/locked using the existing authenticated `driverLocationUpdate` event. The backend adds a success acknowledgement after saving and broadcasting, without changing authorization, status rules or the customer's update event. Deploy that additive backend change before releasing the new driver binary. The Customer App receives the same live updates and does not need to collect the customer's own background location for this feature.

Tracking starts only for DRIVER_GOING_TO_PICKUP / DRIVER_GOING_TO_DROPOFF after foreground and background permission. A short purpose explanation precedes the OS permission flow; refusal leaves foreground features working and does not repeatedly prompt on the same trip. Android displays the delivery foreground-service notification; iOS displays the background-location indicator. Each task callback checks current trip status and authentication before sending. Completion/cancellation and sign-out stop tracking; stale/invalid points are discarded. No historical offline location queue is stored. A separate short-lived socket avoids disturbing screen/chat connections; recent foreground emissions avoid duplicate background updates.

Verify on physical Android/iPhone builds: grant/refuse background permission, minimize and lock during pickup/delivery, see fresh driver coordinates in the Customer App, confirm completion/cancellation/logout stops updates, reconnect after a network outage, and resume after visiting another screen. Test the configured background service and iOS Always permission, including denial and OS settings return. Force-quitting, revoked permission, missing connectivity and OS battery restrictions can prevent delivery of location updates; continuous tracking cannot be guaranteed under those conditions. Old binaries without TaskManager retain foreground functionality until rebuilt.
